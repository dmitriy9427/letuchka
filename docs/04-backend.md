# 04. Бэкенд через интерфейс: локальный и Supabase

## Задача

Пока нет ключей Supabase (или нет сети), приложение должно работать. А когда
ключи есть — работать с настоящим сервером. При этом компоненты и стор не
должны знать, какой вариант подключён.

## Решение: интерфейс + две реализации (паттерн «адаптер»)

`app/lib/backend.ts` описывает, **что** умеет бэкенд:

```ts
type Backend = {
  signIn(name): Promise<User>
  currentUser(): Promise<User | null>
  createRoom(title, user): Promise<string>
  connect(roomId, user, events): Promise<RoomConnection | null>
}
```

`connect` возвращает соединение с комнатой: снимок данных и методы
(`addCard`, `toggleVote`, `setPhase`…), а изменения приходят в колбэки
`events.onChange / onPresence / onCursor / onReaction`.

Две реализации:

| | `localBackend.ts` | `supabaseBackend.ts` |
| --- | --- | --- |
| Хранение | localStorage браузера | Postgres |
| Кто участник | вкладка (sessionStorage) | анонимный пользователь Supabase |
| Реальное время | BroadcastChannel между вкладками | Supabase Realtime |
| Проверка прав | нет (всё в одном браузере) | правила RLS в базе |

Выбор — в `composables/useBackend.ts`: есть ключи в настройках — Supabase,
нет — локальный. Компонентам всё равно.

Плюсы такого устройства:

- можно разрабатывать и показывать проект без сервера;
- логику комнаты проверяют тесты на локальном бэкенде
  (`localBackend.test.ts`: два участника видят изменения друг друга);
- заменить Supabase на Firebase или свой сервер — написать третью реализацию,
  остальной код не меняется.

## Как работает локальный бэкенд

**BroadcastChannel** — встроенный в браузер канал между вкладками одного сайта:

```ts
const channel = new BroadcastChannel('letuchka:abc12345')
channel.postMessage({ kind: 'change', change })   // отправить всем вкладкам
channel.onmessage = ({ data }) => { … }           // получить
```

Изменение данных:

1. прочитать комнату из localStorage;
2. применить изменение (`applyChange`) и записать обратно;
3. применить у себя и разослать другим вкладкам.

**Кто онлайн (presence)** — без сервера это «сердцебиение»: каждая вкладка
раз в 2 секунды шлёт «я здесь». Кто молчит дольше 6 секунд — ушёл (вкладку
закрыли, не успев сказать «пока»). Новичку отвечают сразу, чтобы он не ждал
2 секунды, пока узнает о других. При закрытии вкладки (`pagehide`) шлём «пока».

**Участник = вкладка.** Пользователь хранится в `sessionStorage` (свой у
каждой вкладки), а комнаты — в `localStorage` (общий). Поэтому вторая вкладка
— это второй человек со своим именем и голосами. Сначала пользователь лежал в
localStorage, и все вкладки были одним человеком — демо выглядело как пустая
комната.

## Ошибки

> **Компоненты зовут Supabase напрямую.** Без ключей проект не запустить, без сети — не
> разработать, тесты — только с базой. Интерфейс `Backend` и две реализации.
>
> **Реализации расходятся в правилах.** Обрезка текста до 280 символов — в общих функциях
> (`cleanCardText`, `newCard`), а не в каждой реализации отдельно.
>
> **Участник «висит» после закрытия вкладки.** `pagehide` приходит не всегда. Нужен heartbeat и
> срок жизни (здесь 2 с и 6 с).

## Попробуйте сами

1. Откройте комнату в двух вкладках. Почему это **два разных** участника, хотя браузер один?
2. Закройте одну вкладку «жёстко» (убейте процесс). Через сколько она пропадёт из списка онлайн?
3. Как добавить третью реализацию — например, свой сервер на WebSocket?

<details>
<summary>Ответы</summary>

1. Пользователь хранится в `sessionStorage` — у каждой вкладки своё; комнаты — в `localStorage`,
   общем для всех.
2. До 6–8 секунд: участник, молчащий дольше `PRESENCE_TTL` (6 с), удаляется при очередном
   heartbeat (раз в 2 с).
3. Написать `createWsBackend(): Backend` с теми же методами и выбрать его в `useBackend`.
   Компоненты и стор не изменятся.
