# 05. Supabase: база, права, вход, реальное время

**Supabase** — «бэкенд как сервис» поверх Postgres: база данных, вход
пользователей, файлы и реальное время, доступные прямо из браузера через
`@supabase/supabase-js`. Свой сервер писать не нужно, но и безопасность тогда
обеспечивает **база**, а не ваш код. Это главное, что нужно понять.

## Подключение проекта (один раз)

1. [supabase.com](https://supabase.com) → New project (регион — Frankfurt).
2. **Authentication → Sign In / Providers →** включить **Allow anonymous sign-ins**.
3. **SQL Editor → New query** → вставить `supabase/schema.sql` → **Run**.
4. **Project Settings → API**: скопировать **Project URL** и **publishable
   (anon) key** в `.env` (по образцу `.env.example`) — для локального запуска,
   и в переменные репозитория GitHub (`Settings → Secrets and variables →
   Actions → Variables`: `SUPABASE_URL`, `SUPABASE_KEY`) — для деплоя.
5. Перезапустить `npm run dev` — в шапке пропадёт «Демо-режим».

> **Секретный ключ (service_role / secret) никуда не копируйте.** Он обходит
> все правила доступа. В браузере ему не место.

## Почему публичный ключ можно показывать

Publishable-ключ видит любой, кто открыл сайт, — он в JS-бандле. Он лишь
говорит «запрос из этого проекта». Что можно читать и менять, решают
**правила RLS** в базе: каждый запрос проверяется построчно.

## Таблицы (`supabase/schema.sql`)

```
rooms  — id (8 символов из ссылки), title, owner_id, phase, timer_end, focus_card_id
cards  — id, room_id, column, text, author_id, author_name
votes  — card_id + user_id (первичный ключ — нельзя дважды за одну карточку), room_id
```

`check (...)` в таблицах — проверки на уровне базы: длина текста, допустимые
этапы и колонки. Даже если отправить запрос в обход интерфейса, база не
примет мусор.

`default auth.uid()` — id пользователя из токена запроса подставляет сервер.

## Row Level Security — правила доступа

```sql
alter table cards enable row level security;

create policy "cards create" on cards for insert to authenticated
  with check (author_id = auth.uid() and room_phase(room_id) = 'write');
```

Читается так: «вставлять карточки может вошедший пользователь, если автор —
он сам и комната на этапе "пишем"».

- `using (...)` — какие **существующие** строки видны или изменяемы (select,
  update, delete);
- `with check (...)` — какими могут быть **новые** значения (insert, update).

Правила «Летучки»:

| Таблица | Читать | Создавать | Менять | Удалять |
| --- | --- | --- | --- | --- |
| rooms | все вошедшие | от своего имени | только ведущий | — |
| cards | все вошедшие | свои, на этапе «пишем» | свои, на этапе «пишем» | автор или ведущий |
| votes | все вошедшие | свои, на этапе «голосуем», < 3 в комнате | — | свои, на этапе «голосуем» |

Лимит в 3 голоса проверяется **в базе** — подсчётом голосов пользователя в
комнате прямо в правиле. Интерфейс тоже не даст проголосовать в четвёртый раз,
но это лишь удобство; защита — в базе.

`room_phase()` — маленькая SQL-функция с `security definer` (выполняется с
правами владельца), чтобы правила могли узнать этап комнаты.

Ошибка «нарушено правило» приходит с кодом `42501` — бэкенд превращает её в
понятное «Сейчас это действие недоступно».

### Честно о «скрытых» карточках

На этапе «пишем» чужие карточки размыты **в интерфейсе**, но данные приходят в
браузер — посмотреть их через DevTools можно. Для ретро это нормально (цель —
не подглядывать случайно). Если нужна настоящая тайна, текст надо отдавать с
сервера только после смены этапа: через view с фильтром или Edge Function.

## Вход без регистрации

```ts
await supabase.auth.signInAnonymously({ options: { data: { name: 'Аня' } } })
```

Supabase создаёт настоящего пользователя без почты и пароля и выдаёт токен.
Токен хранится в браузере — при перезагрузке вы тот же человек и остаётесь
ведущим своих комнат. Имя лежит в `user_metadata`.

## Реальное время

У Supabase Realtime три механизма, все — через канал комнаты:

| | Что это | Где в «Летучке» |
| --- | --- | --- |
| **Broadcast** | сообщения между клиентами, без базы | изменения данных, курсоры, реакции |
| **Presence** | общий список «кто онлайн» с автоматическим уходом при отключении | участники |
| **Postgres Changes** | уведомления о вставках и изменениях строк в таблицах | не используется — см. ниже |

**Почему изменения данных идут через Broadcast, а не Postgres Changes.**
Схема такая: действие → запись в базу (там RLS проверяет права) → база
вернула строку → рассылаем изменение остальным Broadcast'ом. База остаётся
источником правды, а Broadcast — быстрым уведомлением.

Postgres Changes удобнее (не нужно рассылать вручную), но у него ограничения:
события удаления нельзя отфильтровать по комнате, а для каждого подписчика
сервер проверяет RLS — на больших комнатах это медленнее. Для ретро на
10–20 человек обе схемы рабочие; Broadcast проще отлаживать.

Минус выбранной схемы: если сообщение потерялось (обрыв связи), участник не
узнает об изменении до перезахода. Улучшение — при восстановлении соединения
заново загружать снимок комнаты.

## Ошибки

> **Права только в интерфейсе.** Кнопку «голосовать» можно обойти запросом из консоли. Правила —
> в RLS.
>
> **`service_role`-ключ во фронтенде.** Он обходит RLS целиком. В браузер — только публичный
> (anon/publishable) ключ.
>
> **RLS включён, политик нет.** Таблица молча возвращает пустоту — «данных нет», хотя они есть.
>
> **Счётчик голосов, который можно обмануть.** Без проверки «карточка из этой комнаты» голос можно
> записать на карточку другой комнаты и обойти лимит. Политика проверяет и это.
>
> **Ждать Postgres Changes для каждого действия.** Медленнее и дороже; здесь база — источник
> правды, а Broadcast — быстрые уведомления.
